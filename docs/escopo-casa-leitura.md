## Riscos e bloqueios

- **Dados existentes no banco:** a V3 e a V100 já gravam `companies.cnpj` como `NOT NULL UNIQUE` (`V1__create_initial_schema.sql:12`) e a aplicação roda com `ddl-auto: validate` (`application.yml:27`) — ou seja, o schema é dono do Flyway, não o Hibernate. Remover a coluna `cnpj` exige uma migration nova (`V5__...`) que também decida o que fazer com os dados já existentes (apagar/arquivar). Não verificado se há dados reais em produção hoje além do seed demo.
- **Autorização por papel inexistente:** `@EnableMethodSecurity` está declarado (`SecurityConfig.java:29`) mas nenhum `@PreAuthorize`/`hasRole` é usado em nenhum controller ou service — qualquer usuário autenticado do tenant (`ADMIN`, `USER` ou `VIEWER`) pode chamar qualquer endpoint, inclusive `DELETE /products/{id}` e `POST /nfce/{id}/confirm`. Isso bloqueia direto a regra "só o dono remove membros" até que autorização por role seja implementada — hoje não há **nenhuma** restrição desse tipo em lugar nenhum.
- **`InvoiceStatus.PENDING` nunca é persistido pelo fluxo atual:** `ProcessNfceUseCase.execute` (`usecase/ProcessNfceUseCase.java:61-69`) sempre constrói a `Invoice` já com `status(InvoiceStatus.FETCHED)`; não há nenhum ponto do código que grave `PENDING` fora do seed manual (`V100__dev_seed.sql:35`). Isso quebra silenciosamente o contador `pendingInvoices` do dashboard (sempre ~0) — listado também em "O que falta".
- **`InvoiceStatus.ERROR` sem nenhum produtor:** busquei `InvoiceStatus.ERROR` em todo `src/main/java` e só aparece na própria declaração do enum (`InvoiceStatus.java:8`) — nenhum fluxo trata falha de consulta fiscal definindo esse status (erros de fetch lançam `FiscalException`, que vira HTTP 5xx/4xx sem persistir nada). Não é um bloqueio para a v1, mas é enum morto que pode confundir quem for alterar o fluxo de revisão.
- **Dependência Bucket4j declarada e não usada:** `pom.xml:134-139` adiciona `bucket4j-core`, mas não há nenhum filtro/bean usando rate limiting em `src/main/java` (busquei por `Bucket4j`/`bucket4j`/`RateLimit` e nada apareceu). Código morto — não bloqueia nada, mas infla o classpath sem função.
- **CORS totalmente aberto:** `allowedOriginPatterns(List.of("*"))` combinado com `allowCredentials(true)` (`SecurityConfig.java:63-67`) aceita requisições autenticadas de qualquer origem. Não é específico da mudança de proposta, mas vale revisar antes de abrir convites para membros fora do ambiente de desenvolvimento.
- **Segredo JWT com valor padrão fraco documentado no próprio YAML:** `application.yml:45` traz `change-this-to-a-very-long-random-secret-key-at-least-256-bits` como default; funciona porque presumivelmente o ambiente de produção sobrescreve via `JWT_SECRET`, mas não há nenhuma checagem que impeça subir em produção com o valor padrão. Não verificado se o deploy atual já define a variável.
- **Teste de integração depende de Docker local:** `AuthControllerIntegrationTest` (Testcontainers) falha neste ambiente Windows por falta de um Docker Desktop acessível via `npipe` (log do build, erro `BadRequestException Status 400`). Isso é ambiental, documentado também no `README.md:76`, não bloqueia a leitura de escopo, mas bloqueia qualquer CI que dependa só deste `mvn verify` sem Docker disponível.
- **Dependência entre repositórios não verificável neste ambiente:** não encontrei os repositórios Stockflow-web/Stockflow-mobile nos diretórios acessíveis desta sessão, então nenhuma afirmação sobre "o que o front consome hoje" pôde ser confirmada lendo código do front — tudo na seção "Contrato com a API" é inferido do lado da API e marcado como tal.
